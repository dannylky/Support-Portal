1. 目的、範圍與系統總覽

目的。 本程序界定石門校園教學空間如何被監察、如何保持課堂就緒，以及如何從故障中復原 — 主要以遙距及自動化方式進行，凡涉及更改裝置的操作，一律設有人手批准閘。

範圍。 課室 SM-11-01 至 SM-11-08 及 Common Area，涵蓋：房內顯示裝置與 AV-over-IP（AVoIP）分發、Extron 房間控制與電源控制、PTZ 觀察攝影機、AVoIP 管理平台、AV VLAN 上的網絡交換機，以及監察上述各項的自動化／監察系統。課堂於 09:00 開始；講台電腦須於 08:30 前就緒。

1.2 運作模式

  • 預設唯讀。 每項排程檢查只作觀察。更改裝置的操作依 §8 執行。
  • 證據次序。 AVoIP 頁（Kramer 縮圖）為主要證據；PTZ 畫面作支援；snapshot.json 作佐證。音訊解碼器不納入就緒／巡邏判定。
  • 單一負責人、單一批准閘。 重置、電源循環及控制按鍵均由站點負責人（Danny）批准，§8.2 所列的常設授權除外。

4. 標準程序

P1 — 晨早開電視（07:05）

觸發：排程 · 範圍：SM-11-01…08（Common Area 除外）· 權限：常設授權（§8.2）

  1. 逐房登入 Extron 控制器，經已驗證的真實頁面路徑同步面板狀態。
  2. 房間電視已開著則跳過。否則按 TV On 一次（房 1：TV On 及 Side TV On — 兩者皆須）。永不直接按 System ON；TV On 會自動觸發它。
  3. 驗證：只有當 TV On 及 System ON 均已定住（閃爍停止、狀態穩定為「開」）才算成功 — 房 1 另須 Side TV On 狀態定住。
  4. 驗證失敗的房間只重試一次（每房每朝最多 2 次嘗試）。登入失敗或 HTTP 502 = 該房失敗並記錄原因；永不猜測憑證。
  5. 最後檢查：以唯讀方式重讀每間房，兩次取樣相隔約 15 秒。兩次取樣均顯示定住的開著狀態，該房才算定住。
  6. 重試後仍閃爍／未定 → 依 §8.2 的 Option A 處理（只限晨早一輪）。處於穩定非開啟狀態的房間，會直接報告為「電視熄咗（穩定、非閃爍）」，不作電源循環升級。

P2 — 晨早就緒檢查（08:15／08:20）

觸發：排程 · 範圍：SM-11-01…08 · 目標：每間房於 09:00 上課前 READY；講台電腦 08:30 前就緒

  1. 第一階段（08:15）逐格掃描 AVoIP 縮圖頁；仍回傳 404 的格以快速武裝後重試輪次再探測（最多 10 輪）。本階段不作判定。
  2. 第二階段（08:20）按其餘證據（最多再 5 輪）判定每間房 READY／NOT READY：PC 編碼器送出即時畫面、電視解碼器在線並有畫面，並以 PTZ 及快照數據佐證。音訊解碼器忽略；Common Area 除外（預定停用）。
  3. 遲醒房間依 §5.5 記錄 — 只作追蹤，永不視為故障。
  4. 遇解碼器／顯示側故障，本輪會在主對話詢問站點負責人 — 絕不自行行動。經他確認後：房 02/07/08 使用「Reset all decoders」一次；房 01/03/04/05/06 以 P3000 逐部重啟該房的電視解碼器（音訊解碼器除外）。其後覆查並報告。
  5. PC 來源黑畫面個案並非解碼器故障：檢查講台電腦電源及 Windows 顯示模式 — 必須是 Duplicate 而非 Extend（§7.4）。

P3 — 每小時校園巡邏（07:30–22:30）

觸發：排程，每小時 :30 · 範圍：所有房間（Common Area 會掃描，但只在出現預期外情況時報告，§5.4）

  1. 擷取每間房的 PTZ 畫面，並從監察快照讀取裝置狀態。
  2. 逐房記錄：燈光（開／關／局部）、使用中或閒置、按受監察清單的顯示狀態、SM-11-01/02/07/08 的多顯示同步、每個編碼器及電視／音訊解碼器的在線狀態，以及最高 KDS 溫度。
  3. 為房 01–08 執行控制面板閃燈檢查（P4）。
  4. 異常嚴格依 §5.2 判定 — 「未知」永不視為故障，燈光本身亦永不單獨構成異常。
  5. 以一張合併房間表（相片、狀態、燈光、顯示 + 同步、編碼器、解碼器、其他觀察）發出 HTML 報告；以電郵附橫向 A4 PDF 寄出；主旨以該輪狀態開頭。

P4 — 控制面板閃燈檢查（每次巡邏內，以及 P1 的最後檢查）

方法：唯讀 · 經面板狀態觀察工具逐房取樣兩次、相隔約 15 秒（只觀察同步訊框 — 不發送同步指令、永不點擊）

  1. 取樣 System ON 及 TV On 狀態兩次（房 1 另加 Side TV On）。
  2. 兩次取樣均為定住開啟 → 正常。兩次均為同一非開啟狀態 → 穩定關閉：直接報告，並非故障。
  3. 兩次取樣不同，或出現未定／閃爍特徵 → 閃爍 = 異常，在報告異常欄置頂列出。
  4. 遇閃爍房間：為該房／個案建立一張 USS Help Desk 記錄（已預先批准，§8.2）並報告其 CaseID；另行請求負責人批准 PCU 電源循環（§7.6）— 巡邏永不自行執行循環。（只在 07:05 晨早一輪，改依 §8.2 的 Option A。）
  5. 登入失敗／HTTP 502／憑證來源讀取失敗 = 「未能檢查」 — 屬檢查本身的限制，永不視為故障，亦永不單獨構成異常。

P5 — AVoIP 日誌擷取與每日整合

觸發：每 2 小時，08:00–22:00 · 範圍：30 個日誌目標，房 1–8（Common Area 除外）· 唯讀

  1. 經 P3000 協議查詢每部裝置的日誌狀態並擷取其日誌尾段；分析來源中斷事件、重新鎖定、USB 錯誤風暴及「無空間」錯誤。
  2. 來源中斷個案（解碼器緩衝以未重新鎖定作結，或一間房在時窗內有 2 次或以上來源中斷）：將該房的 PTZ 快照及 Manager 縮圖隨該輪儲存作證據。
  3. 22:00 一輪另整合全日（每日總結），並對全部 16 部 AV 交換機作唯讀交叉核對（登入狀態、記錄等級、與晨早基線比較的計數）。
  4. 自動化永不清除日誌。清除日誌（LOG-ACTION 4）須經負責人明確批准，且在錯誤風暴仍在運行時通常會被拒絕（§11）。

P6 — 路線看門狗

觸發：運作時窗內每 10 分鐘 · 經遙距存取路徑對一部 PTZ 攝影機及 AV 處理器作唯讀探測

  1. 一輪探測只在兩個子網探測同時失敗時才算失敗（單一探測失敗屬背景資料，並非中斷）。
  2. 連續兩輪失敗 → 向 ShekMun 對話發出「路線中斷」警示。其後首個正常輪次 → 「路線已復原」。其餘時間保持沉默。
  3. 看門狗永不觸碰任何裝置；其存在是為了讓網絡路徑故障在下一輪巡邏或上課前已被知悉。

5. 分類與判定規則

5.1 證據次序

先看 AVoIP 頁（Kramer 縮圖），PTZ 作支援，snapshot.json 作佐證。單一弱訊號永不足以判定故障。

5.2 異常準則（巡邏／就緒）

  • KDS 裝置溫度 ≥ 49 °C。
  • 監察數據中明確的裝置故障狀態。
  • 攝影機離線（Common Area 除外，§5.4）。
  • 經確認的多顯示不同步狀態 — 嚴格判定，通常須連續兩輪成立 — 房 1 例外除外（§5.3）。
  • P4 檢查下控制面板燈閃爍／未定。

以下各項本身不構成異常：燈光狀態；狀態為「未知」的裝置（未知 ≠ 故障）；來源側 NO SIGNAL（電腦關機／休眠並非解碼器故障）；完成整個武裝後重試流程後仍未能取得的縮圖（屬「縮圖未能提供」 — 但見 §5.6）。

5.3 房 1 例外（SM-11-01）

規則： 在 SM-11-01，任何一部電視關閉／黑屏、而房內任何其他電視開著（運作中或待機），即時判為 不同步／異常 — 不設降級的「檢查區域」，不設兩輪等待。四部電視同時關閉屬正常一致關閉。（老師在課堂上手動關掉側邊電視是已知的無害解釋，經確認後個案即結案。）

5.4 Common Area — 預定停用

Common Area 的攝影機及解碼器按安排離線。此狀態屬預期之內，並會在巡邏報告中完全略去（不列行、不提及）。只在出現預期外狀態時才報告 — 裝置重新上線、房間有人使用、燈光開啟或顯示裝置啟動 — 並標示為預期外。

5.5 遲醒

如一間房的 PC 編碼器在就緒第一階段顯示 NO SIGNAL、但到第二階段已送出即時畫面並判為 READY，該房記錄為遲醒。記錄附上甦醒時間括弧（最後 NO SIGNAL 時間 → 首次有畫面時間；確實時刻永不虛構）。遲醒只作追蹤：並非故障、永不判為異常、永不升級、無補救措施。不屬遲醒：PC 來源黑畫面；到判定時仍 NO SIGNAL 的房間（屬 NOT READY）；已復原的縮圖 404。如第一階段數據缺失／不完整，當日早上不作任何遲醒判定。

5.6 不顯示縮圖的解碼器

解碼器在快照數據中正常、但完成整個武裝後重試流程後其 Manager 縮圖仍回傳 404，會分類為 NEEDS-RESTART，並在任何重啟之前先升級通知負責人。已驗證的補救方法是對該解碼器發出 P3000 #RESET（經內部網絡接受指令、無需登入）。

7. 事故處理手冊

每個已知問題的逐個案處理 — 症狀、逐步處理及不應做的事，按重要性排序 — 載於配套頁面 已知問題案例處理。以下手冊概述該等個案所依賴的關鍵技術。

7.1 Manager 縮圖回傳 404

縮圖必須先武裝：首次請求會啟動擷取並回傳 404；每約 0.5 秒重試（最多 10 次）即會回傳圖像。請求不得帶有 Connection: close 標頭（Manager 對該等請求一律回傳 404）。完成整個流程後仍 404 的縮圖屬「縮圖未能提供」，並非裝置故障 — §5.6 適用時除外。

7.2 解碼器重置路線

  • 主要（所有房間）： 在該房 Companion 按「Reset all decoders」；以快照數據及縮圖驗證復原。
  • 後備： 只對電視解碼器逐部發出 P3000 #RESET；音訊解碼器永不經此等路線重置。
  • 兩條路線均須先經負責人確認（§8），已批准的就緒補救（P2 第 4 步）除外。

7.3 Kramer Manager 網頁介面當機

如 Manager 的網頁服務當機（TCP 有回應、TLS 握手停滯），P3000 介面在 TCP 5000 仍會回應且無需登入：發出 #RESET 即可重啟 Manager，約 80 秒完全復原（網頁介面約 30 秒）。網頁管理憑證並非 SSH 憑證，永不會如此試用。

7.4 就緒時 PC 來源黑畫面／NO SIGNAL

  1. 檢查講台電腦已開機（且未卡在進入 Windows 之前）。
  2. 檢查 Windows 顯示模式：必須是 Duplicate。在 Extend 模式下，編碼器接收的是空白的延伸桌面 — 此為 2026-10-15 房 7 個案的已證實成因。
  3. 檢查連接編碼器的 HDMI 線及編碼器的 PoE／網絡狀態。
  4. 來源側故障不要重置解碼器。

7.5 交換機管理登入失敗

艦隊交換機平常經 HTTP 提供其 API。房 1 一對交換機於 2026 年 10 月韌體升級後，會將 HTTP 重新導向至 4443 埠的 HTTPS 並回傳空白內文，表面上看似「空白登入」失敗。擷取工具因此會自動改用 HTTPS（TLS 1.2）；同一密碼仍然有效 — 重新導向／空白回應屬傳輸方式改變，並非憑證改變。注意：升級後的一對交換機，其從屬機的緩衝日誌可能只回傳一行，主機的記錄等級顯示為 5（艦隊其他主機為 6）— 屬數據注意事項，並非故障。

7.6 AV 處理器電源循環（PCU 升級）

  1. 先決條件：閃爍／未定的面板個案（§P4），或負責人的直接指示。
  2. 只使用該房的 PCU-AVRack 插座 4（永不用 PCU-Lectern）：關 → 約 10 秒 → 開，經該裝置的網頁 SIS 介面操作。
  3. 待控制器開機、重新同步面板，並以相隔約 15 秒的兩次取樣加 PTZ 確認。
  4. 批准：須經負責人逐案批准，07:05 晨早一輪依 Option A 者除外（§8.2：每房每朝最多一次循環 + 一次復原 System ON 按鍵；其後仍閃爍 = 停止、報告、詢問）。

7.7 電視解碼器的 USB 錯誤風暴

重複的 USB 錯誤行（嚴重時伴隨「No space left on device」）顯示實體 USB 路徑出現問題。清除日誌（LOG-ACTION 4）在風暴仍運行時只會重新填滿，故不獲批准作為修復方法；持久的補救方法是實地檢查 USB 路徑。繼續觀察並報告；不要清除日誌。

8.1 批准閘

除 §8.2 的常設授權外，任何更改裝置的操作均不會在未經站點負責人確認下進行。提案必定述明確實的裝置、證據及干擾最少的補救方法，並等候回覆。

8.2 常設授權（負責人批出、現行有效）

  • Option A — 晨早一輪的閃爍處理（由 2026-10-23 起）： 閃爍觸發會在該輪內全程處理（一次 PCU 循環 + 每房每朝最多一次復原按鍵；其後仍閃爍 → 停止、報告、詢問）。日落條款：連續 3 個早上沒有閃爍個案後，此預先授權即告失效，該輪回復先問後做；只有負責人可重新授權。

8.3 升級路徑

  • 排程一輪發現的故障 → 在該輪報告中匯報；向負責人（主對話）提出補救建議，只在確認後執行，其後覆查並以跟進報告結案。
  • 控制面板閃爍（巡邏） → Help Desk 記錄（CaseID 格式 U-YYYYMMDDHHMMSS）+ 向負責人提出 PCU 批准請求。
  • 路線中斷（看門狗） → 向 ShekMun 對話發警示；在任何裝置操作前，先沿網絡路徑（遙距存取路徑 → 子網路由器 → 交換機）調查。
  • Teams 存取規則： 經瀏覽器存取 Microsoft Teams 嚴格只限 USS Help Desk 對話；不會開啟任何其他對話，非閃爍個案的發文每次均須負責人批准。

9. 報告與分發

  • 巡邏報告： 每份報告一張合併的房間為本表格（房間 · 相片 · 狀態與觀察 · 燈光 · 顯示 + 同步 · 編碼器 · 解碼器 · 其他），送遞至 ShekMun 對話，並以電郵寄出自包含 HTML 連橫向 A4 PDF 附件。電郵主旨以該輪狀態開頭：Status OK 或 Status ABNORMAL。
  • 就緒報告： 逐房判定表，附遲醒欄及遲醒總結行；以電郵寄出並在「ShekMun report」Gmail 標籤下加上標籤及歸檔。
  • 分發： 石門巡邏及就緒報告電郵只寄往負責人指定的 Gmail 地址（2026-10-11 更改）。負責人的工作電郵不在此分發名單上。
  • 語言： 所有排程送遞均以廣東話、繁體中文書寫，並使用 §5.7 的用語。
  • 預訂參考： 巡邏按該星期的合併課室預訂參考（時間表圖像 + 預訂試算表）判定，該參考存放在巡邏目標的檔案下。
  • WhatsApp： 巡邏／報告不能從其他對話經 WhatsApp 送遞；報告在指定對話及以電郵送遞。

10. 保安與安全

  • 所有遙距存取只經安全遙距存取及站點子網路由器到達站點；沒有管理介面對外公開。
  • 憑證只會在運行時從其安全來源即時使用，永不寫入文件、記憶檔案、報告或本程序。禁止猜測密碼：登入失敗會連同原因如實報告為失敗。
  • 監察工作均為唯讀。唯一會更改裝置的排程工作是晨早開電視一輪，且在其書面限制之內（§8.2）。
  • 電源切換只限 §7.6 下的 PCU-AVRack 插座 4。PCU-Lectern 插座永不用於處理器重啟。
  • 有疑問時，自動化會停下並詢問。錯過一次檢查可以補回；上課期間未經授權的裝置操作則不能。
