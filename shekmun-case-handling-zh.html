案例 1 控制面板燈號閃爍／未定 緊急

如何識別

一間房的 Extron 面板按鈕（System ON／TV On — 房 1 另有 Side TV On）未能定住：相隔約 15 秒的兩次狀態取樣不一致，或一次按鍵後燈號仍在閃爍。由 07:05 晨早一輪、巡邏閃燈檢查發現，或由老師報告。

逐步處理

  1. 以唯讀方式取樣兩次，相隔約 15 秒。兩次均定住開啟 → 並非本案例。兩次均為同一非開啟狀態 → 穩定關閉：直接報告為「電視熄咗（穩定、非閃爍）」並停止 — 只有閃爍的按鈕才足以支持 PCU 重啟。
  2. 如確認閃爍，先分清這是 07:05 晨早一輪，還是巡邏／其他時間 — 處理方式不同（第 3 步對第 4 步）。
  3. 晨早一輪（Option A，已預先授權）： 將該房的 PCU-AVRack 插座 4 電源循環一次（關 → 約 10 秒 → 開）。待控制器開機並重新同步。如房間自行復原，即完成。如它穩定地關閉而電視開著，按 System ON 一次。以兩次取樣 + PTZ 確認。其後仍閃爍 → 停止、報告、詢問負責人。
  4. 巡邏／任何其他時間： 為該房建立一張 USS Help Desk 記錄（閃爍個案已預先批准），並在報告中註明其 CaseID；其後請求負責人批准 PCU 循環 — 在晨早一輪以外，永不在未經批准下執行。
  5. 在該輪的異常欄中將該房列在首位；閃爍屬異常準則之一。
切勿： 使用 PCU-Lectern 插座；每房每朝循環多於一次；為一間穩定關閉的房間提議 PCU 重啟。
經驗註記： SM-11-01 是重複出現的房間（連續多個早上閃爍，均在該輪內依 Option A 處理定住；其 Help Desk 記錄同日已建立並解決）。連續三個早上無閃爍個案，Option A 預先授權即自動失效。

案例 2 上課前房間未就緒 — 解碼器／顯示側故障 緊急

如何識別

就緒第二階段將一間房判為 NOT READY：PC 訊源有即時畫面，但有顯示裝置黑屏、電視解碼器離線，或 AVoIP 證據顯示畫面未能到達螢幕。

逐步處理

  1. 確認故障屬顯示／解碼器側而非來源側：PC 編碼器顯示即時畫面（如否，轉到案例 3）。
  2. 按固定次序收集證據：AVoIP 縮圖 → PTZ 畫面 → 快照狀態／溫度。
  3. 在主對話向負責人升級，附上房間、證據及建議的補救方法。等候確認 — 就緒一輪永不自行行動。
  4. 確認後，按房組別施行補救方法一次：房 02/07/08 → 「Reset all decoders」（Companion）。房 01/03/04/05/06 → 以 P3000 #RESET 逐部重啟該房的電視解碼器（音訊解碼器除外）。
  5. 重跑該房的就緒證據，在 09:00 上課前報告 READY 或仍 NOT READY。
切勿： 按「Source: PC」作為補救；重置音訊解碼器；在未報告首次結果下重複重置。

案例 3 PC 訊源無信號／黑畫面 — 來源側 高

如何識別

房間的 PC 編碼器顯示 NO SIGNAL 或黑畫面，而解碼器及顯示裝置均健康。在報告中這是無視訊來源信號 — 屬來源問題，並非解碼器故障。

逐步處理

  1. 檢查講台電腦已開機並已過 BIOS／開機程序（休眠或關機的電腦是最常見成因）。
  2. 檢查 Windows 顯示模式：必須是 Duplicate。在 Extend 模式下，編碼器接收的是空白的延伸桌面，房間便會黑屏而表面上一切「運作正常」。
  3. 檢查連入編碼器的 HDMI 線是否插穩，以及編碼器有否 PoE／網絡。
  4. 如電腦甦醒並在下一個排程輪次前畫面回復，將其記錄（如符合遲醒模式，見案例 12）— 無需任何裝置操作。
  5. 如訊源到上課時間仍無畫面，向負責人升級並附上已完成的檢查；下一步通常是實地檢查電腦。
切勿： 為來源側故障重置解碼器或 AV 處理器 — 這無濟於事，只會干擾房間。
經驗註記： 2026-10-15 房 7 的 NOT READY 正是本案例 — Windows 處於 Extend 模式。此後它成為每個 PC 來源黑畫面個案的第一項檢查。

案例 4 多顯示不同步 高

如何識別

在多顯示房間（SM-11-01、02、07、08），各螢幕狀態不一致：一部黑屏／關閉，而其他顯示內容或待機畫面。須綜合 PTZ + 解碼器狀態判定。

逐步處理

  1. 先看房 1 例外： 在 SM-11-01，任何一部電視關閉／黑屏而任何其他一部開著 = 即時判為不同步／異常 — 不設第二輪等待。四部同時關閉屬正常一致關閉，並非本案例。
  2. 其他房間：在連續兩輪巡邏中確認後，才判為不同步（單一畫面可能剛好捕捉到轉換訊源的一刻）。
  3. 在升級為故障前，先排除無害成因：老師在課堂上手動關掉一組電視（在房 1 已多次確認 — 個案隨即以人手操作結案，並非故障）。
  4. 檢查黑屏顯示裝置的解碼器：快照中在線？縮圖有即時畫面？溫度正常？如問題在解碼器本身，轉到案例 6。
  5. 連同證據報告為異常；提出干擾最少的補救方法，並等候負責人確認。
切勿： 將房 1 個案降級為「檢查區域」，或在課堂時間內未先核查人手操作的解釋便提出顯示故障。

案例 5 路線中斷 — 監察路徑故障 高

如何識別

看門狗發出「路線中斷」警示：連續兩輪探測中，攝影機子網及 AV 處理器兩個探測同時失敗。問題持續期間，遙距甚麼也看不到、檢查不到 — 但房間本身可能完全正常。

逐步處理

  1. 不要從缺失的數據診斷房間故障：在路線復原前，任何巡邏／就緒結論均不成立。
  2. 依次序調查路徑：操作員的安全遙距存取 → 站點子網路由器 → 兩個 AV 子網（172.18.2.0/24 及 172.18.22.0/24）。
  3. 分清整條路線故障（兩個子網）與單一裝置故障（只有一個探測失敗 — 那是背景資料，並非本案例）。
  4. 當一輪探測再次成功，看門狗會報告「路線已復原」；恢復正常排程，並在當日報告中註明缺口。
  5. 如中斷將覆蓋 09:00 上課時間，立即通知負責人 — 因遙距就緒無法核實，可能需要實地支援。
切勿： 因監察當時看不到，便將房間標記為故障，或重跑已錯過的裝置操作。
經驗註記： 2026-10-12 的子網中斷正是看門狗存在的原因；它只在狀態改變時發警示，所以一次中斷只會產生兩則訊息（中斷、復原）。

案例 6 解碼器正常但縮圖永遠 404 — 需要重啟 高

如何識別

一部電視解碼器在快照數據中健康（在線、溫度正常），但其 Manager 縮圖永遠載入不到，而其他房間的縮圖正常。

逐步處理

  1. 以武裝後重試方法重新擷取縮圖：首次請求會武裝擷取（出現 404 屬預期），每約 0.5 秒重試、最多 10 次。請求不得發送 Connection: close — Manager 對該等請求每次都回傳 404。
  2. 如在任何一次重試中取得圖像，那只是擷取暖機 — 並非個案。無需記錄。
  3. 如完成整個流程後仍 404 而且解碼器在快照中正常，將該解碼器分類為 NEEDS-RESTART（需要重啟）。
  4. 在任何重啟之前，連同證據向負責人升級。
  5. 經確認後，以 P3000 #RESET 重啟該一部解碼器（無需登入），並核實縮圖已復原。
切勿： 將首次嘗試的 404 報告為故障，或在升級前重啟 — 在武裝後重試行為被證實之前，正是這種誤讀造成了多次假警報。
經驗註記： 已在 SM-11-01 TV-DEC-1 上證實 — 經 P3000 重啟後縮圖復原。假 404 的根源在我方（請求方式 + 擷取武裝），不在 Manager。

案例 7 電視於轉換訊源時重啟／偶發 KDS 信號中斷 中

如何識別

Fujitsu IW862/IW982 電視（房 1、2、7、8）在轉換訊源時（PC ↔ 手提電腦、轉堂）重啟或失去畫面，或解碼器短暫失去信號（日誌中先出現視信來源終止、後出現視訊來源恢復）。

逐步處理

  1. 確認鏈路每一環都遵守全站視訊規則：電腦及 AVoIP 裝置均為 1920×1080、50 Hz。60 Hz 是已知會令此等電視視訊不穩定的觸發因素。
  2. 取出該時窗的解碼器日誌證據（每 2 小時的擷取通常已保存），並註明中斷是否自行重新鎖定。
  3. 檢查解碼器的溫度及在線狀態，排除硬件故障（如有異常，轉到案例 6/2）。
  4. 在問題調查檔案中追蹤個案：房間、時間、轉換訊源的背景、日誌摘錄。不要即興更改設定。
  5. 已議定的緩解候選 — 提高電視解碼器的顯示行為延遲（休眠／關機延至約 300 秒，喚醒維持 0 秒）— 只在負責人決定時才施行。
切勿： 歸咎於 HDCP 或重新鎖定的頻繁 — 調查已排除兩者；觸發點是轉換訊源時進入 720p60 待機信號的格式轉換。

案例 8 解碼器陷於探索循環 中

如何識別

一部電視解碼器在其日誌中重複重新探索／重新鎖定，而其鄰近裝置穩定；房間畫面可能以重複模式閃爍或中斷。

逐步處理

  1. 從日誌擷取確認循環的只是單一部解碼器，並註明其循環速率。
  2. 在 Manager 中檢查該解碼器的頻道指派：循環出現的充要條件是其頻道選擇延伸家族中至少一組未被指派（「null」） — 通常是 USB 家族。
  3. 向負責人報告發現，附上確實的裝置及找到的未指派家族。
  4. 補救方法（由負責人執行或指示）：在 Manager 中為該解碼器指派該等未指派的延伸家族。循環會於數秒內停止 — 無需重啟。
  5. 在下一次日誌擷取中核實循環已消失，並記錄該裝置為已修復。
切勿： 將解碼器恢復出廠設定（重置亦可能重新啟用 CEC 閘道 — 見標準操作程序的已知問題），或更改 Manager 的頻道方案，那是正確的。
經驗註記： 已在 SM-11-03 TV1 上證實 — 指派後數秒內循環停止。其餘循環中的裝置，在負責人選擇時以同一方法修復。

案例 9 USB 錯誤風暴／解碼器日誌爆滿（「No space left on device」） 中

如何識別

一部電視解碼器的日誌充斥 USB 錯誤行（數十行一組地爆發），有時伴隨重複的 「No space left on device」 錯誤，通常在系統開啟時一次來源重新鎖定後隨即開始。

逐步處理

  1. 從日誌擷取辨認裝置及風暴時窗；確認畫面及教學不受影響（通常不受影響）。
  2. 只繼續觀察：在每 2 小時的擷取中追蹤風暴是否仍在運行。
  3. 不要清除日誌。LOG-ACTION 4 清除曾被評估並明確不獲批准：風暴運行期間日誌會重新填滿，清除只會毀掉證據而修復不了任何東西。
  4. 持久的補救方法是為該解碼器作實地實體 USB 路徑檢查（線材、埠、所連裝置）— 如風暴持續，與負責人安排。
  5. 在每日總結中報告新出現的風暴裝置；已知裝置仍在風暴中屬追蹤事項，不會重複升級，除非畫面受影響。
切勿： 清除日誌、將重置解碼器當作「修復」，或重複提議負責人已押後的實地檢查 — 只作觀察是常設決定。

案例 10 Kramer Manager 網頁介面當機 中

如何識別

Manager 的網頁介面無法載入（TCP 有連接、TLS 握手停滯），而各裝置繼續運作。縮圖及由 Manager 驅動的檢查均不可用。

逐步處理

  1. 確認當機只限網頁服務：Manager 在 TCP 5000 仍回應 P3000 協議。
  2. 在負責人指示下，經 P3000 #RESET 重啟 Manager — 該協議無需登入。
  3. 等候約 80 秒待完全復原（網頁介面通常約 30 秒回復；P3000 先回應）。核實介面能載入、縮圖回復。
  4. 在當日報告中註明事件及復原時間。
切勿： 拿網頁管理憑證去試 SSH（它們並非 SSH 憑證，嘗試會被拒絕），或將死掉的網頁介面視為艦隊故障 — AVoIP 裝置會繼續運行。

案例 11 交換機管理登入突然失敗 中

如何識別

22:00 的交換機交叉核對開始將一間房的一對交換機報告為「空白／非 JSON 登入」，而我方並無作任何更改，交換機亦明顯仍然存活。

逐步處理

  1. 先探測、後下結論：請求交換機的 HTTP 根路徑並查看原始回應。301/308 重新導向至 4443 埠 HTTPS 並帶空白內文，代表該交換機現已強制使用 HTTPS 管理 — 所謂「空白登入」其實是被解析的重新導向內文。
  2. 經 HTTPS 檢查韌體版本及運行時間：在最後一次正常檢查與首次失敗之間發生升級 + 重啟，是連貫的成因（房 1 一對交換機於 2026-10-20 正是如此）。
  3. 核實同一個密碼可經 HTTPS 4443 登入，且序號／型號與基線相符 — 同一裝置、新韌體、憑證無更改。
  4. 擷取工具已能處理此情況：先 HTTP，整段擷取自動後備至 HTTPS 4443。如新的一對交換機出現同一症狀，在報告失敗前先確認後備已啟動。
  5. 記錄升級後機對的數據注意事項（從屬機的緩衝日誌可能只回傳一行；主機記錄等級可能顯示 5 而非 6）— 屬注意事項，並非故障。
切勿： 報告密碼已被輪換、要求新憑證，或將交換機改回 HTTP 管理 — 該裝置端更改只屬負責人的決定。

案例 12 遲醒 — PC 訊源遲到，房間 READY 無需行動 — 只作記錄

如何識別

一間房的 PC 編碼器在就緒第一階段（08:15）顯示 NO SIGNAL，但送出即時畫面並在第二階段（08:20）判為 READY。該電腦只是甦醒得遲。

逐步處理

  1. 在第二階段報告中將其記錄為遲醒：該房在遲醒欄的行、總結行，以及數據檔。
  2. 如實記錄甦醒時間括弧：最後 NO SIGNAL 時間 → 首次有畫面時間。永不虛構確實的甦醒時刻。
  3. 到此為止。遲醒是追蹤記錄，令此模式變得可量度（哪些房間、遲了多久）— 單次出現不會引發任何後續行動。
切勿： 將房間標記為異常、升級，或施行任何補救。不屬遲醒：黑畫面的 PC 來源（屬案例 3）、到判定時仍 NO SIGNAL 的房間（屬 NOT READY）、或已復原的縮圖 404。如第一階段數據缺失，當日早上不要作任何遲醒判定。

案例 13 Common Area 意外重新上線 中 — 只作報告

如何識別

Common Area 處於預定停用：其攝影機及解碼器離線是正常狀態，平常在巡邏報告中完全略去。本案例恰恰相反 — 其攝影機／裝置重新上線、房間有人使用、燈光開啟，或顯示裝置啟動。

逐步處理

  1. 在該輪巡邏報告中包括 Common Area（略去規則的唯一例外），並將狀態標示為預期外。
  2. 如實報告所見（裝置上線、燈光、顯示、有人），不要判為故障 — 為活動而蓄意開機是較可能的解釋。
  3. 不要作任何裝置操作。如狀態跨輪次持續且無解釋，在報告的注意事項行向負責人提及。
切勿： 將任何裝置「熄回預定停用」，或在任何一輪中將其正常的離線狀態報告為故障。
