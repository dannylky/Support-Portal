1. Purpose, scope and system overview

Purpose. This SOP defines how the Shek Mun campus teaching spaces are monitored, kept ready for classes, and recovered from faults — mostly remotely and automatically, with a human approval gate for anything that changes a device.

Scope. Rooms SM-11-01 to SM-11-08 and the Common Area, covering: in-room displays and AV-over-IP (AVoIP) distribution, Extron room control and power control, PTZ observation cameras, the AVoIP management platform, network switches on the AV VLANs, and the automation/monitoring stack that watches them. Classes start at 09:00; lectern PCs must be ready by 08:30.

1.2 Operating model

  • Read-only by default. Every scheduled check observes only. Device-changing actions follow §8.
  • Evidence order. AVoIP page (Kramer thumbnails) is the primary evidence; PTZ views support; snapshot.json corroborates. Audio decoders are excluded from readiness/patrol judgements.
  • One owner, one gate. The site owner (Danny) approves resets, power cycles and control presses, except the standing authorisations listed in §8.2.

4. Standard procedures

P1 — Morning TV ON (07:05)

Trigger: schedule · Scope: SM-11-01…08 (Common Area excluded) · Authority: standing authorisation (§8.2)

  1. For each room, log in to the Extron controller and sync panel state through the proven real-page route.
  2. If the room's TVs are already on, skip the room. Otherwise press TV On once (Room 1: TV On and Side TV On — both required). Never press System ON directly; TV On triggers it.
  3. Validate: the press is successful only when TV On and System ON have settled (flashing stopped, state settled at “on”) — Room 1 also requires the Side TV On state settled.
  4. A room that fails validation is retried exactly once (maximum 2 attempts per room per morning). Login failure or HTTP 502 = room failed with reason; never guess credentials.
  5. Final check: re-read every room read-only, two samples ~15 s apart. A room settled only if both samples agree on the settled-on state.
  6. Flashing/unsettled after retry → the Option A handling in §8.2 (morning run only). A room in a stable non-on state is reported plainly as “TV off (stable, not flashing)” with no power-cycle escalation.

P2 — Morning readiness check (08:15 / 08:20)

Trigger: schedule · Scope: SM-11-01…08 · Goal: every room READY before 09:00 classes; lectern PCs ready by 08:30

  1. Stage 1 (08:15) sweeps the AVoIP thumbnail page cell by cell; still-404 cells are re-probed in quick arm-and-retry rounds (up to 10). This stage makes no verdict.
  2. Stage 2 (08:20) judges each room READY / NOT READY on the remaining evidence (up to 5 further rounds): PC encoder feeding a live image, TV decoders online and fed, corroborated by PTZ and snapshot data. Audio decoders ignored; Common Area excluded (scheduled down).
  3. Late-wake rooms are recorded per §5.5 — tracking only, never a fault.
  4. On a decoder/display-side fault, the run asks the site owner in the main chat — it never acts by itself. After his confirmation: Rooms 02/07/08 use “Reset all decoders” once; Rooms 01/03/04/05/06 restart that room's TV decoders one by one via P3000 (audio decoder excluded). Then re-check and report.
  5. A PC-source-black case is not a decoder fault: check the lectern PC's power and the Windows display mode — it must be Duplicate, not Extend (§7.4).

P3 — Hourly campus patrol (07:30–22:30)

Trigger: schedule, hourly at :30 · Scope: all rooms (Common Area scanned but reported only on an unexpected case, §5.4)

  1. Capture each room's PTZ view and read device status from the monitoring snapshot.
  2. Per room record: lighting (ON / OFF / partial), in use or idle, display state per monitored inventory, multi-display sync for SM-11-01/02/07/08, every encoder and TV/audio decoder's online status, and the highest KDS temperature.
  3. Run the control-panel flash check (P4) for Rooms 01–08.
  4. Judge abnormalities strictly by §5.2 — “unknown” is never a fault, and lighting alone is never abnormal.
  5. Issue one merged room table (photo, status, lighting, display + sync, encoders, decoders, other observations) as the HTML report; email it with a landscape A4 PDF; prefix the subject with the run status.

P4 — Control-panel flash check (within each patrol, and in P1's final check)

Method: read-only · Two samples ~15 s apart per room via the panel-state observer (observes sync frames only — sends no sync command, never clicks)

  1. Sample System ON and TV On states twice (Room 1 also Side TV On).
  2. Both samples settled-on → normal. Same non-on state in both samples → stable off: report plainly, not a fault.
  3. Samples differ, or an unsettled/flashing signature → flashing = ABNORMAL, named first in the report's anomalies.
  4. On a flashing room: create one USS Help Desk record for the room/case (pre-approved, §8.2) and report its CaseID; separately request the owner's approval for a PCU power cycle (§7.6) — the patrol never performs the cycle. (In the 07:05 morning run only, Option A §8.2 applies instead.)
  5. Login failure / HTTP 502 / credential-source failure = “check not possible” — a limitation of the check, never a fault and never abnormal by itself.

P5 — AVoIP log capture and daily consolidation

Trigger: every 2 h, 08:00–22:00 · Scope: 30 log targets, Rooms 1–8 (Common Area excluded) · Read-only

  1. Query each unit's log state and tail its log over the P3000 protocol; analyse for source-loss events, re-locks, USB error storms, and “no space” errors.
  2. Source-loss case (a decoder buffer ending without re-lock, or 2+ source-loss events in a room in the window): save the room's PTZ snapshot and Manager thumbnails as evidence with the run.
  3. The 22:00 run additionally consolidates the day (daily summary) and cross-checks all 16 AV switches read-only (login state, logging levels, counters vs the morning baseline).
  4. Logs are never cleared by automation. A log clear (LOG-ACTION 4) needs the owner's explicit approval and is normally refused while an error storm is still running (§11).

P6 — Route watchdog

Trigger: every 10 min in the operating window · Read-only probes of one PTZ camera and the AV processor over the remote access path

  1. A round fails only if both subnet probes fail (a single-probe failure is context, not an outage).
  2. Two consecutive failed rounds → “route down” alert to the ShekMun chat. The next OK round after that → “route recovered”. Silent otherwise.
  3. The watchdog never touches a device; it exists so a network-path failure is known before the next patrol or class.

5. Classification and judgement rules

5.1 Evidence order

AVoIP page (Kramer thumbnails) first, PTZ in support, snapshot.json to corroborate. A single weak signal never decides a fault.

5.2 Abnormal criteria (patrol / readiness)

  • KDS device temperature ≥ 49 °C.
  • An explicit device failure state in the monitoring data.
  • A camera offline (except Common Area, §5.4).
  • Confirmed out-of-sync multi-display state — strictly judged, normally requiring two consecutive runs — subject to the Room 1 exception (§5.3).
  • Control-panel lights flashing / unsettled under the P4 check.

Not abnormal by themselves: lighting state; a device whose status is “unknown” (unknown ≠ fail); a source-side NO SIGNAL (a PC that is off/asleep is not a decoder fault); a thumbnail that is still unavailable after the full arm-and-retry pass (that is “thumbnail unavailable” — but see §5.6).

5.3 Room 1 exception (SM-11-01)

Rule: in SM-11-01, any one TV off/dark while any other TV in the room is on (active or standby) is OUT OF SYNC / ABNORMAL immediately — no downgraded “check region”, no two-run wait. All four TVs off together is normal uniform off. (A teacher manually switching off the side TVs during class is the known benign explanation and closes the case when confirmed.)

5.4 Common Area — scheduled down

The Common Area camera and decoders are offline by arrangement. That state is expected and is omitted from patrol reports entirely (no row, no mention). It is reported only if an unexpected state appears — devices back online, room in use, lights on, or display active — and is then flagged as unexpected.

5.5 Late wake （遲醒）

A room is recorded as late wake when its PC encoder showed NO SIGNAL in readiness Stage 1 but feeds a live image and is READY by Stage 2. The record carries the wake bracket (last NO SIGNAL time → first IMAGE time; the exact moment is never invented). Late wake is tracking only: not a fault, never ABNORMAL, never an escalation, no remedy. Not late wake: a black PC source; a room still NO SIGNAL at the verdict (that is NOT READY); a recovered thumbnail 404. If Stage 1 data is missing/incomplete, no late-wake calls are made that morning.

5.6 Decoder that will not show a thumbnail

A decoder that is normal in the snapshot data but whose Manager thumbnail keeps returning 404 after the full arm-and-retry pass is classified NEEDS-RESTART and escalated to the owner before any restart. The proven remedy is a P3000 #RESET of that decoder (it accepts the command over the private network with no login).

7. Incident playbooks

Scenario-by-scenario handling for every known issue — symptoms, step-by-step handling, and what not to do, ordered by importance — is maintained in the companion page Case Handling for Known Issues. The playbooks below summarise the key techniques those cases rely on.

7.1 Manager thumbnail returns 404

Thumbnails must be armed: the first request starts the capture and returns 404; retrying every ~0.5 s (up to 10 attempts) returns the image. Requests must not carry a Connection: close header (the Manager answers those with 404). A thumbnail still 404 after the full pass is “thumbnail unavailable”, not a device fault — unless §5.6 applies.

7.2 Decoder reset routes

  • Primary (all rooms): the room's Companion “Reset all decoders” press; verify recovery in the snapshot data and thumbnails.
  • Fallback: per-decoder P3000 #RESET for TV decoders only, one by one; audio decoders are never reset by these routes.
  • Either route requires the owner's confirmation first (§8), except inside an approved readiness remedy (P2 step 4).

7.3 Kramer Manager web interface hangs

If the Manager's web service hangs (TCP answers, TLS handshake stalls) the P3000 interface still answers on TCP 5000 with no login: a #RESET reboots the Manager, with full recovery in ~80 seconds (web UI ~30 s). Web-admin credentials are not SSH credentials and are never tried as such.

7.4 PC source black / NO SIGNAL at readiness

  1. Check the lectern PC is powered (and not stuck before Windows).
  2. Check the Windows display mode: it must be Duplicate. In Extend mode the encoder is fed the blank extended desktop — the proven cause of the 2026-10-15 Room 7 case.
  3. Check HDMI into the encoder and the encoder's PoE/network state.
  4. Do not reset decoders for a source-side fault.

7.5 Switch management login failures

Fleet switches normally serve their API over HTTP. After the Room 1 pair's firmware upgrade (Oct 2026) those two switches redirect HTTP to HTTPS on port 4443 with an empty body, which reads as an “empty login” failure. The fetch tooling therefore falls back to HTTPS (TLS 1.2) automatically; the same password works — a redirect/empty response is a transport change, not a credential change. Note: on the upgraded pair the satellite's buffered log may return only one line, and the master's logging level reads 5 (fleet masters otherwise 6) — data caveats, not faults.

7.6 AV processor power cycle (PCU escalation)

  1. Preconditions: a flashing/unsettled panel case (§P4), or the owner's direct instruction.
  2. Use the room's PCU-AVRack outlet 4 only (never PCU-Lectern): OFF → ~10 s → ON, via the unit's web SIS interface.
  3. Allow the controller to boot, re-sync the panel, and confirm with two samples ~15 s apart plus PTZ.
  4. Approval: the owner's per-case approval is required, except in the 07:05 morning run under Option A (§8.2: at most one cycle + one recovery System ON press per room per morning; still flashing after that = stop, report, ask).

7.7 USB error storm on a TV decoder

Repeated USB error lines (with “No space left on device” in severe cases) indicate a physical USB-path problem. Clearing the log (LOG-ACTION 4) only refills while the storm runs and is not approved as a fix; the durable remedy is an on-site USB-path field check. Continue observation and report; do not clear logs.

8.2 Standing authorisations (owner-granted, in force)

  • Morning TV ON (from 2026-10-13/15): the 07:05 run may press TV On as specified in P1 without per-morning approval.
  • Option A — flashing handling in the morning run (from 2026-10-23): a flashing trigger is handled end-to-end inside the run (one PCU cycle + at most one recovery press per room per morning; still flashing → stop, report, ask). Sunset: after 3 consecutive mornings with no flashing case, this pre-authorisation expires and the run reverts to ask-first; only the owner can re-authorise it.
  • Flashing-case Help Desk records (from 2026-10-30): one record per room per flashing case is posted directly and its CaseID reported; this covers ticket creation only.
  • Scheduled report emails: the scheduled jobs send their report emails without a per-run approval prompt, to the designated distribution only.

8.3 Escalation paths

  • Fault found by a scheduled run → reported in the run's report; remedy proposed to the owner (main chat) and executed only on confirmation, then re-checked and closed out in a follow-up report.
  • Control-panel flashing (patrol) → Help Desk record (CaseID format U-YYYYMMDDHHMMSS) + PCU approval request to the owner.
  • Route down (watchdog) → alert to the ShekMun chat; investigation follows the network path (remote access path → subnet router → switches) before any device action.
  • Teams access rule: browser access to Microsoft Teams is strictly limited to the USS Help Desk chat; no other chat is opened, and non-flashing posts need the owner's approval each time.

9. Reporting and distribution

  • Patrol reports: one merged room-based table per report (Room · Photo · Status & observations · Lighting · Display + sync · Encoders · Decoders · Other), delivered to the ShekMun chat and emailed as self-contained HTML with a landscape A4 PDF attachment. Email subjects begin with the run status: Status OK or Status ABNORMAL.
  • Readiness reports: per-room verdict table with a late-wake column and a late-wake summary line; emailed and labelled/archived under the “ShekMun report” Gmail label.
  • Distribution: Shek Mun patrol and readiness report emails go to the owner's designated Gmail address only (changed 2026-10-11). The owner's work email is not on this distribution.
  • Language: all scheduled deliveries in Cantonese, Traditional Chinese characters only, using the terminology in §5.7.
  • Booking references: patrols are judged against the week's merged classroom booking reference (timetable images + booking spreadsheet), maintained under the patrol goal's files.
  • WhatsApp: patrol/report delivery over WhatsApp is not available from other chats; reports are delivered in the designated chats and by email.

10. Security and safety

  • All remote access reaches the site only through secure remote access and the site subnet router; no management interface is exposed publicly.
  • Credentials are used transiently at runtime from their secure sources and are never written into documents, memory files, reports or this SOP. Password guessing is prohibited: a login failure is reported as a failure with its reason.
  • Monitoring jobs are read-only. The only scheduled device-changing job is the morning TV-on run, within its written limits (§8.2).
  • Power switching is restricted to PCU-AVRack outlet 4 under §7.6. PCU-Lectern outlets are never switched for processor restarts.
  • When in doubt, the automation stops and asks. A missed check is recoverable; an unauthorised device action during class is not.
